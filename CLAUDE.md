# HOSA Bayview training platform

Web app for HOSA Bayview, the HOSA chapter at Bayview Secondary School. HOSA is a health science competition organization with many competitive events. This is a training platform, similar to Google Classroom, where members study and practice for their events.

## How to work

- Build in phases (see PLAN.md). After each phase: run the app, test it, fix bugs, run /adversarial-review, commit and push.
- Use relevant skills (impeccable first for any UI, then frontend-design).
- UX matters as much as features: every screen needs sensible empty, loading, and error states, and must work one-handed on a phone.

## Tech stack

- Next.js 16 (App Router, TypeScript, `src/`), Tailwind CSS v4. Read `node_modules/next/dist/docs/` before using Next APIs; this version differs from older training data.
- Supabase for auth, Postgres, and file storage. `@supabase/ssr` for cookies.
- Roles enforced with Row Level Security in Postgres, not just hidden in the UI.
- Deploy target: Vercel (GitHub integration, push to `main` deploys). Repo: `claudeforeveryone/hosa-bayview` (GitHub's push redirect named it on 2026-10-12; it was `claudemaxforeveryone-hue/hosa-bayview` after the 2026-10-10 move from idontreallyknow-20; old URLs redirect, idontreallyknow-20 keeps write access, and cloud sessions are scoped to `idontreallyknow-20/hosa-bayview`, which reaches it through the redirect) (**public** since 2026-10-10, so cloud sessions on the shared Claude account can clone it). Everything committed is world-readable: secrets stay in Vercel/Supabase env, never in the repo, and new code comments name roles ("an executive"), not people or emails.
- Migrations live in `supabase/migrations/` and are applied with the Supabase MCP.

## Authentication

- Sign up, log in, log out, and password reset with email and password. Email confirmation is OFF.
- New accounts default to Trainee. Executives can change any user's role.
- First Executive: granted by uid through `private.exec_granters` (0201 retired the email-based sign-up promotion; see Security notes).

## Roles

1. Executive (admin): full access. Sees all users, trainers, trainees, classrooms, tests, flashcards, files, links, stats. Can change roles and edit or delete any content.
2. Trainer: creates and manages their own classrooms. Sees and manages only trainees in their own classrooms. Adds tests, flashcards, files, and links to their classrooms.
3. Trainee: joins classrooms with a join code. Studies flashcards, takes tests, creates own flashcards, views leaderboards.

## Global leaderboard (all of HOSA Bayview)

- Rankings: most time on site, most questions answered, most questions correct, accuracy.
- Filters: all time (default), today, this week, this month, in a dropdown beside the measure dropdown.
- `BoardView` (client) switches measure, period and page in place, never by navigation (a reload swapped in the loading screen and jumped to the top): another period loads through the `loadBoard` server action, and the address follows with `history.replaceState` (`metric`, `period`, `page`). Full boards show 20 a page with arrows, page numbers and Find me (`src/lib/board-pages.ts`); Home's short board has no pages.

## Classrooms

- One per HOSA event. Trainers create with name, event, description, and get a join code.
- Trainees can be in multiple classrooms.
- Tabs: Overview, Questions (a dropdown: Tests, Cards; `src/lib/classroom-tabs.ts`), Resources, People, Attendance, and for managers Grades and Settings.
- Leads (0291): `classrooms.lead_ids` (ordered, not granted to clients) are the people who run a room. `owns_classroom` counts a lead, so a lead sees the room and, as a trainer or executive, manages it; `my_classrooms`/`classroom_detail` give the leads' names as `owner_name` ("A, B & C") and `is_owner` for a lead; Ask teacher reaches the leads; the People tab lists them (`classroom_runners`). Executives set them in a room's Settings > Who runs it (`set_classroom_leads`, trainers or executives only, at most 6, logged `leads`). No leads = the maker shows as before. The chapter's lead list was loaded by a one-off SQL script, never committed (it names people). Tests: `supabase/tests/classroom_leads.sql`.

## Career

- Career Questions tab: search, test filter and a "Quiz yourself on these" box; the quiz and flashcard pages take `set`, `test` and `q`.

## Flashcards

- Trainers and trainees create decks. Trainer decks are shared with the classroom. Trainee decks are private by default, optional share to classroom.
- Study mode: flip, shuffle, mark known / still learning.
- Bulk add by pasting term and definition pairs.

## Testing

- Multiple choice only.
- Bulk import by pasting past competition tests:
  ```
  1. Question text?
  A. Option
  B. Option
  C. Option
  D. Option
  Answer: B
  ```
- Preview after parsing so the trainer can fix mistakes before saving.
- Manual add, edit, delete, with optional explanation per question.
- Modes: timed test and untimed practice. Auto grade server-side; show results with correct answers and explanations.
- Every attempt is saved and counts toward stats and leaderboards. Answer keys are never readable by trainees before they submit.

## Activity tracking

- Heartbeat once a minute while the tab is visible and the user isn't idle. Stored one row per user per minute so it can't be inflated.
- Questions answered and correct per user, per classroom.
- Online status for "who's online" (seen in last 2 minutes).
- Elo (0080-0083, 0105) is the sum of `elo_events` from 0, no base. Developers (stats viewers, `private.stats_viewers`) can set a member's Elo on /developer > Members (`dev_set_elo`, 0292): one `adjust` row with the difference (can be negative, no classroom, dated now, `ref_id` = the developer), logged `elo`; executives who aren't developers can't. Tests: `supabase/tests/dev_set_elo.sql`. Answers on published tests count for everyone (managers included): first answer to a question 2, +3 if right; answering it again 1, or 2 if right, once per question per Toronto day (`repeat`). Plus reviews, daily sign-in and lucky bonuses, scaled by the study streak multiplier. On a test that hides its answers (`show_answers` off) an answer earns the same right or wrong (2 first time, 1 repeat, no `correct` row), so Elo and the correct count can't give the key away; when the test shows its answers again, the held-back bonus is paid with the date and multiplier it was earned on (0205, `private.elo_pay_revealed`). An answer reads `show_answers` under a share lock on the test row, so an answer and a reveal running at once can't skip a bonus (`supabase/tests/elo_reveal_lock.sql`).

## Legal and SEO

- `/terms` and `/privacy` (route group `(legal)`) describe what the site really collects and who can read it (the privacy page's "Who can see it" follows the RLS and definer functions, role by role). When a feature starts storing something new about members, or lets a role read more, update the privacy page (text in `privacy/policy.tsx`) and bump `LEGAL_EFFECTIVE` in `src/lib/legal.ts`. Lines for push notifications, usage counts and the feedback form show only when `POLICY_COVERS` (`src/lib/legal.ts`) says that feature is in the build; `privacy/privacy.test.ts` fails until each flag matches `supabase/migrations` (push_subscriptions, analytics_events, feedback), so merging one of those features means flipping its flag. Contact and independence wording live there too; pages render the independence line with `<IndependenceNote />` (keeps "HOSA-Future" whole). Sections get an "On this page" list automatically from `<LegalSection>` children. The full-screen intro never plays on these two pages (`NO_INTRO_PATHS`, `src/lib/intro.ts`).
- Housekeeping in the daily cron route (`src/app/api/keepalive/route.ts`), after `keepalive()`, runs only when `HOUSEKEEPING=on` is set (off by default: it deletes live rows and files, so it waits for the owner's yes, migrations 0250 and 0251 and `SUPABASE_SECRET_KEY` in production). While it's off the privacy page promises no retention deadline for wrong codes or deleted accounts' pictures; once it runs in production the page may say two days (bump `LEGAL_EFFECTIVE`). `purge_attempt_logs()` (0250, publishable key) drops wrong join/sign-up code logs older than 22 hours (the Hobby cron fires anywhere in its hour, so runs can be 25 hours apart), and deleted accounts' picture files (listed by `orphan_avatar_files()`, 0251, secret key only) are erased through the Storage API (SQL can't delete storage files). The sweep erases nothing when more than 3 accounts or a quarter of all pictures look orphaned. Any failure answers 500 and logs `[keepalive] housekeeping failed`. Deleting an account: `docs/DELETE_ACCOUNT.md`.
- Private by default: the root metadata and the `X-Robots-Tag` header in `next.config.ts` are noindex. A page is indexable only if it is in all four places: public in `src/lib/route-gate.ts`, `INDEXED_PATHS` in `src/lib/seo.ts` (robots.txt allow list, sitemap), the `X-Robots-Tag` override in `next.config.ts`, and `publicPage()` metadata (canonical, card). Tests check they agree. The logo, app icons and social card files (`/icon.png`, `/apple-icon.png`, `/opengraph-image.png`, `/twitter-image.png`) have their own index rule in `next.config.ts`, because the JSON-LD logo must be indexable (`src/lib/robots-header.test.ts`).

## Chapter-wide features (all events, not just MC)

- Notifications (0052): `notifications` rows written only by triggers or definer jobs (new announcement, event, day-of event reminder, published class test, trainer reply, Ask teacher question to the room's owner or execs (0099), role change, new competition), never by clients. Bell in the sidebar and phone bar polls `unread_notifications()`; on /notifications, opening one marks it read and "Mark all as read" clears the rest (`mark_notifications_read(ids)`); just visiting the page reads nothing. Each row has a bin, and "Clear read" deletes the read ones on the page, by id (0281, `dismiss_notifications(ids)`: stamps your own rows `dismissed_at` and marks them read; the inbox hides them; it's an update, not a DELETE, because the Supabase MCP won't apply DELETE; the privacy page says deleted notices are kept until the account goes). Applied on live 2026-10-12; the page falls back to listing everything with no delete controls if the column is missing (42703). Tests: `supabase/tests/dismiss_notifications.sql`.
- Push (0220-0221, Omega PWA track): every `notifications` row also goes out as a Web Push (VAPID, `web-push`). `push_subscriptions` (one row per browser endpoint; members read/delete their own, change only `sound`; written through `push_subscribe()`, which checks the push-service allowlist and returns the row id). A statement-level AFTER INSERT trigger on `notifications` queues rows in `private.push_outbox` for members with a device and pokes `/api/push/deliver` through pg_net; that route is public in `route-gate.ts` because the database has no session, and it is gated only by the `x-push-secret` header (`PUSH_INTERNAL_SECRET` in Vercel = vault secret `push_internal_secret`; no vault row means push is off and nothing is queued). The route claims with `push_claim` (3 min lease), sends (`src/lib/push/deliver.ts`), reports with `push_report`: 404/410 drops a device, 10 failures in a row too, and a 429/5xx/timeout keeps the notification queued for the devices that missed it (`delivered`, 5 tries, 1-4 min apart). The route starts no claim or wave of 10 pushes after 40 s and gives each push 12 s, so it always reports inside its 60 s; what it had no time to try goes back as `untried`, which gives the try back. pg_cron jobs `hosa-push-sweep` (every minute, re-pokes) and `hosa-push-history` (prunes cron history). Devices follow the session: the subscribe route keeps the row id in the HttpOnly `hosa-push-device` cookie, `logout()` deletes that row, password changes delete the member's other rows, `/login` unsubscribes the browser, and every signed-in page re-saves the device with its Notification sound setting (`usePushDeviceSync`). Service worker `public/sw.js` (offline page `/offline`, push and click handlers; bump `VERSION` when its precache changes). Tests: `supabase/tests/push.sql`, `src/lib/push/*.test.ts`.
- Announcements (0052): `classroom_id` null = chapter-wide (/announcements, executives post, edit, pin); otherwise shown at the top of the classroom Board tab (the room's managers post). Posting notifies the audience. /announcements is an inbox (0280, `announcement_states`: each member's own `read_at`/`deleted_at`, readable and writable only by them): headline as the subject line, unread rows bold on the highlight colour with a New tag, read rows on the band. /announcements/[id] opens one with Mark as read/unread and Delete announcement (removes it from your list only); executives also pin, edit and Delete for everyone there. ## Security notes

- First executive: the email bootstrap is retired (0201). `private.maybe_promote_first_exec` is a no-op and `private.settings.first_executive_email` is never read. Executives are granted by uid only, by a chapter lead or by hand in the SQL editor (see `supabase/tests/roles.sql`).
- Profiles are deleted only by deleting the auth user (admin API); the last executive can't be demoted or deleted. Executives can do it in the app: /admin > Remove account (`remove_member()`, 0033, deletes the auth user in SQL and the app then erases the profile's current picture file; an upload never saved to the profile, or a failed erase, still leaves a file); a deletion in the Supabase dashboard leaves the file, to delete by hand (`docs/DELETE_ACCOUNT.md`; the daily sweep catches it once `HOUSEKEEPING=on`).
- DB checks in `supabase/tests/` (roles, classrooms, admin_passcode, test_teaching, activity, chapter_tools and the rest; each runs in a rolled-back transaction and raises on failure). Run them with the Supabase MCP `execute_sql`. `chapter_tools.sql` covers 0050-0056.
- The Supabase MCP refuses DROP, DELETE and writes to `auth.*` in `apply_migration` (and DELETE in `execute_sql`); write migrations with CREATE OR REPLACE / ALTER POLICY.
- Banned members can still read rooms they belong to at the DB level (`can_view_classroom` has no ban check); the app sends them to /banned and the ban triggers block writes. Deleting a classroom (owner or /admin) removes its stored files first, while its managers still have storage access. Unit tests: `npm test`.
- Threat model: users are vetted chapter members (selective HOSA application), not the open internet. Keep RLS and role checks strict, but skip anti-abuse work like IP throttling or multi-account brute-force defence. The per-account join-code limit (10 misses / 10 min) is enough; accepted by the owner.
- Join codes are readable only through `my_classrooms`/`classroom_detail` (managers only); the column is not granted on the table.
- Omega security (0200-0207). Hidden scores: `attempts.score` is not granted to clients (scores come only through `attempt_list`, `classroom_tests`, `test_results` and the other RPCs that mask hidden-answer scores, 0200), and Elo no longer gives away whether a hidden answer was right (0205). `can_use_gif`/`gif_exempt_ids` answer for yourself, or everyone for an executive (0202); clients can't insert or delete `profiles` rows (0203). Member data: the bulk name-and-role list `member_directory()` is for executives (0204, the /members page is executive-only), and the bulk `member_details()` gives grade and title only on your own row or to an executive (0206); a member page reads one row through `member_detail(uid)`. That trims bulk reads to what the UI needs; it is not a wall between members: any signed-in member can still open any member's page (name, role, grade, title, stats) and `leaderboard('all')` lists every member by name, by design. What keeps strangers out of member data is the chapter code (0090) once an executive sets one. Checks: `supabase/tests/security_0200.sql` (set `omega.trainee_id`/`omega.exec_id` to pick accounts).
